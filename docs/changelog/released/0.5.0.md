# 0.5.0 — 2026-08-20

## macos

Paste into: App Store Connect (macOS)

Written, not assembled — 43 changes do not fit this store's cap. Every one of them is in the appendix below.

**English**

```
Senders and contacts now show their photo where your account has one, and coloured initials where it does not, in place of the envelope icon. Contacts come across from accounts you sign in to.

Drag on the calendar grid to create, move and resize events, and your calendar is on screen the moment the app opens.

The folder pane stays as you left it, shows each folder's unread count, gives known folders their proper names, and its edge can be dragged to widen it for long account addresses.

Pick light or dark yourself, or keep following the system.

In the composer: nested bullets, table rows and columns, and text colour; typing "- " starts a bullet list; the editor's own buttons now speak the app's language; and it opens on the fields a message usually needs.

Search says how far back it looked, so an empty answer never reads as "there is no such message".

Invitations: answer one on an account whose calendar server will not answer for you; the older copy of a re-sent meeting stops pretending it can still be answered; an answer that could not be delivered says so; and an invitation shows on its own day preview, zoomed in far enough to read what it clashes with.

Removing an account is where you would look for it: Settings → Accounts, as well as the sidebar. There is an About page, and keeping less mail frees the space right away. The Mac app goes by its own name.

If you use the MCP server, copy the config snippet from Settings → Advanced again — the relay moved inside the app and older configs point at the old location.

Faster: the mail list opens at once however much mail you have, the app stays responsive during a first sync, new mail arrives with less waiting, and the list no longer jumps when a background sync starts.

Fixed: reply-all keeps every recipient. A refused password says so instead of blaming the server, and one refused folder no longer asks you to sign in again. A sign-in whose token the provider rotates is saved the moment it changes. A sent message always leaves a copy in Sent. A forward stays in the conversation it came from, and a message you open stays in its conversation. Folder names with an ampersand or non-Latin characters read correctly.
```

**Deutsch**

```

Eine Anmeldung, deren Token der Anbieter erneuert, wird sofort gespeichert. Eine gesendete Mail hinterlässt immer eine Kopie in Gesendet. Eine Weiterleitung bleibt in ihrer Unterhaltung, und eine geöffnete Mail bleibt in ihrer Unterhaltung. Ordnernamen mit Kaufmanns-Und oder nichtlateinischen Zeichen werden richtig angezeigt.

## Changes in this release

Engineering commentary, carried over from each fragment. Never pasted into a store.

### A quiet note when mail is catching up — `a-quiet-note-when-mail-is-catching-up` (macos, ios, windows, android, linux, minor)

> A background pass used to be promoted to the download bar as soon as it committed anything, so a
> poll tick or a boot catch-up took a row of layout for work the user never started. That row is
> now reserved for a download they are actually waiting on; a background pass instead names itself
> in a status line each client already draws — which account is catching up, and how far through
> its folders the pass is.
>
> It appears only once the pass has actually committed a message, so a poll that finds nothing
> stays silent, and the sync that follows the user's own archive or send says nothing at all (it
> does download — the moved message is re-committed — and the row already left the list).
>
> The account is named from the client's own account list rather than an id on the wire, and
> several at once collapse to a count with their folder totals summed. Two debug-only staging
> hooks hold either surface up long enough for a UI suite to measure, because a real pass against
> a local fixture is up for a fraction of a second.

### The composer opens on the fields a message usually needs — `a-shorter-composer-header` (macos, ios, windows, linux, minor)

> Cc and Bcc now sit behind a chevron on the To row, as they already did on Android and as Gmail and
> Thunderbird draw them, so the header a new message opens with is From, To, Subject. The rows open
> by themselves over anything the app put in them — a reply-all's Cc, and on Windows a `mailto:`
> link's Bcc — because a recipient the sender cannot see is one they cannot remove
> (docs/composer-security.md, Gate 12). Each client decides that from the seeded addresses in one
> pure function its own suite drives.

### Answering an invitation works on an account whose calendar server will not answer for you — `answer-an-invitation-on-an-imap-calendar-account` (macos, ios, windows, android, minor)

> A Microsoft invitation delivered to an IMAP mailbox with a CalDAV calendar could not be answered:
> Accept reported "your answer wasn't sent", and the meeting never appeared in the calendar either.
> Nothing on that deployment moves an iMIP message from the mailbox into the calendar, and **no RFC
> assigns that job to anyone** — RFC 6638 governs the scheduling a server performs on calendar
> operations, not a bridge from a mail store. So the meeting was on no calendar, and the answer had
> nothing to write to. Advertising `calendar-auto-schedule` does not change that, which is the part
> that made this hard to see: `caldav.soverin.net` advertises it, so the account looked entirely
> capable right up to the button. Answering now files the meeting first — the invitation's own bytes
> with its `METHOD` stripped (RFC 4791 §4.1), under a guarded create so a copy the server deposited
> is found rather than overwritten — which is the attendee flow RFC 6638 §3.2.2 describes. Where the
> calendar server does not schedule at all, the core also builds the iTIP `REPLY` and posts it as an
> iMIP message itself (RFC 5546 §3.2.3, RFC 6047 §2.4), so the organizer is told by the one route
> that is left; that account then gains a note field and an "email the organiser" toggle it never
> had, because on that route both are ours to honour. Whether an account can answer at all is now
> read from what can actually be **delivered** — the engine's new `calendar_scheduling` and
> `scheduling_submission` — rather than from whether the calendar could store a `PARTSTAT`, which
> was never the same question. Verified live against both states of a real CalDAV server.

### Drag on the calendar grid to create, move and resize — `calendar-drag` (macos, ios, android, minor)

> Three gestures, one rule underneath: **what crosses the FFI is how far the hand moved**, in whole
> days and minutes, never the clock the block was dropped under. That is what lets a meeting in
> another time zone be dragged on a device set to a different one without re-timing it for everybody
> else, lets a segment clipped by midnight be dragged at all, and makes a move preserve its duration
> bit-identically. `docs/calendar.md` §10 has the full reasoning, including the two designs it
> rejects.
>
> Deliberately narrow in two places. Only the user's **own** events lift — their appointments and the
> meetings they organise — because re-timing somebody else's meeting behind their back is a
> *proposal* (iTIP `COUNTER`), not a move, and that is a feature of its own. And a **repeating** event
> asks *This event · All events* before it writes anything: the core exposes an occurrence token and
> refuses to guess, so dragging one Tuesday standup cannot rewrite every Tuesday to eternity.
>
> Windows and Linux ship nothing here, and they are the hard cases rather than the leftovers — a
> Windows precision touchpad hands the app a phase-less wheel, so a drag has no begin or end to hang
> off. Not in this release; named in "Known gaps".

### Choose light or dark yourself — `choose-light-or-dark-yourself` (macos, ios, windows, android, linux, minor)

> Settings → General → Appearance. It follows the system by default, exactly as before, and keeps
> following it live; Light and Dark are an explicit override for anyone whose desktop setting is not
> what they want their mail in. Persisted in the core beside the other display preferences, so the
> clients cannot disagree about it, and read straight off disk before the first frame so the window
> never flashes the scheme the user said they did not want.
>
> It also gives us a lever we did not have: `MAILCAL_APPEARANCE=light|dark|system` pins a debug
> launch to either theme, so screenshots and UI checks stop depending on how the machine is set.
>
> Known gap: the composer editor and a message's own body stay light, on every platform — both are
> HTML in a web view with no dark palette. That was already true on a dark desktop.

### Typing "- " at the start of a line starts a bullet list — `composer-hyphen-starts-a-bullet-list` (macos, ios, windows, android, linux, minor)

> The autoformat every word processor has, in the shared editor so it lands on every client at once:
> a hyphen and a space at the start of a line replace themselves with a bullet, and the line becomes
> the first item. Whatever was already after the caret on that line comes with it.
>
> It fires only when the text between the start of the line and the caret is **exactly** the marker,
> so a hyphen anywhere else in a sentence is left alone. Two places it deliberately does not fire:
> inside an existing list item, where the marker is text the user meant to type; and inside a table
> cell, where the document schema gives a cell inline content only — a list built there would be
> flattened into loose text on send, which is worse than not firing. Every guard can only make it
> trigger less often, never more, and the failure mode is the literal "- " that would have been
> typed anyway.

### Nested bullets, table rows and columns, and text colour in the composer — `composer-nested-lists-tables-and-colour` (macos, ios, windows, android, linux, minor)

> Three gaps in the rich composer, all in the shared editor bundle so they land on every client at
> once. Bullets could not nest: the document schema and the Rust renderer have always carried
> sub-lists, but nothing in the editor could make one, and Tab inserted a literal tab. Tables could
> only be created, never reshaped. And a run could be bold, italic, underlined or resized, but not
> coloured.
>
> Indent/outdent and the table shape commands are written as DOM transforms rather than
> `execCommand`, which emits a `<blockquote>` outside a list — flattened into loose paragraphs by the
> document reader — and nests differently in Blink and WebKit. Every table operation preserves the
> rectangular, non-empty shape Rust validates, so deleting the last row or column removes the table
> instead of producing one that fails to send. Colour is normalized to `#rrggbb` in the editor and
> re-validated by `mailcal_composer::TextColor` on submit, because the value goes straight into a
> `style` attribute; size, colour and highlight share one `<span>` rather than nesting three.
>
> The editor is now built from TypeScript sources under `clients/composer/src` with a unit suite
> (bun + happy-dom) and a gate step that fails when the committed bundle does not match them.

### Contacts on Linux, under a switcher that stays put — `contacts-on-linux` (linux, minor)

> The Linux client now has the Contacts surface every other platform ships: the unified A–Z list of
> people beside one person's detail, with search pushed into the core so a person past the page cap
> is still findable, and read-only said in as many words rather than left to be inferred. The core
> needed nothing — the join, the ordering, the section letter and the monogram all arrive decided,
> and the client adds no matching of its own. A merged row carries "In N accounts" and its detail
> names them under "Also in"; a person in one account gets neither, because there is nothing to
> disambiguate. Names and organizations are the server's text, so every row is built with Pango
> markup off before the text is set — an address book is full of ampersands.
>
> The destination switcher moved out of the folder pane's header into a bottom bar of the same
> toolbar view, which is where Windows already keeps it. That placement is the point rather than a
> tidy-up: a bar's height is reserved before the accounts get theirs, so the tree scrolls behind it
> and an account with fifty folders can no longer carry the calendar, contacts and settings off
> screen. The three surfaces are one toggle group, so "the calendar and contacts at once" cannot be
> written down; lighting a button to match the model is deliberately silent, because the shell also
> reaches a surface by other routes — opening a message, clicking a folder — and each of those would
> otherwise dispatch a second navigation.
>
> Not wired: the composer's recipient autosuggest and recipient pills, which share the same people
> index but are a separate feature. They stay ⬜ in `docs/contacts.md`.

### Conversations open in place on Linux, and unread mail is bold — `conversations-open-in-place-on-linux` (linux, minor)

> The Linux client listed a conversation as a single summary row that opened its latest message and
> nothing else — the rest of the thread, the account owner's own Sent replies included, was in the
> snapshot and never drawn. A conversation is now an `AdwExpanderRow`: GNOME's own disclosure, at the
> trailing edge rather than the leading gutter macOS and Windows use, revealing every message on the
> thread as nested rows (sender, preview, a Sent badge) and reading the latest one in the pane —
> tapping a nested row reads that one instead. Which conversations are open is host state, so a
> background sync rebuilding the list leaves an open one open; the disclosure is deliberately absent
> from the render-diff key, so toggling one doesn't rebuild the list under its own animation. It
> offers no Archive conversation: that client ships no mail actions yet.
>
> Unread is now carried by weight, on the subject and the sender, matching every other platform. On
> GTK that is CSS, and each row states its own weight rather than leaving it to inherit — a
> conversation's messages are drawn *inside* the row holding the conversation's weight, so a reply
> already read came out bold under an unread thread. The regression test reads the weight PangoContext
> resolved for the rendered label, not the property we set, because the property is the same either
> way. The row's date moved out of the sender line into its own trailing label, so it stays regular.
>
> The three glyphs the list uses to say something — a conversation, read and unread mail — are now
> shipped with the app, compiled into a GResource and registered on the icon theme, because naming
> them out of the theme meant they said different things on different distributions: Ubuntu's Yaru
> draws `mail-replied-symbolic` as a bare arrow where Adwaita draws an envelope. A theme can only
> replace a name it ships, so `mailcal-*` is ours everywhere; the attachment paperclip stays themed,
> because it is the same paperclip in every set and the app should still look native.

### The folder pane stays as you left it, and shows what is waiting — `folder-pane-stays-put-with-unread-counts` (macos, ios, windows, android, minor)

> Three changes to the accounts-and-folders pane, which behaved as though every navigation were also
> a request to tidy it away.
>
> **It stays open.** Expansion used to *be* the selection: the pane showed the selected account's
> folders and nobody else's, so clicking All Inboxes, the account next door, the calendar or
> contacts emptied it, and every launch started collapsed. Any number of accounts can now stand

> across restarts — in the core, so all platforms agree and it survives a reinstall of the client.
> A newly added account opens showing its folders.
>
> **Unread counts.** Each folder carries one, and All Inboxes sums the inboxes. The number is the
> **server's**, not a count of what has been synced — so it matches the number the user's other
> mail client shows even when their sync depth is three months and the mailbox holds years. That
> needed the engine to carry it: JMAP and Graph already return it on the folder object, and IMAP
> now asks for it alongside the folder list (one round trip via LIST-STATUS where the server has

>
> **Role icons.** Inbox, Drafts, Sent, Archive, Junk and Trash each get their own icon, from the

>
> Gmail folders show no count yet: the labels-list call returns none, and asking per label would be

> Clicking a folder did nothing while All Inboxes was showing: no list change, no header change, and

### A flag change no longer refetches the message — `a-flag-change-no-longer-refetches-the-message` (macos, ios, windows, android, linux, patch)

### Mail arriving in the background no longer loses an account's renewed sign-in — `background-sync-keeps-a-renewed-signin` (macos, ios, windows, android, patch)

> The sibling of the replay fix, with a different cause: not a network failure, but an ordering one.
> Renewing a sign-in can hand back a replacement refresh token, which the core re-persists by
> finding the account in its registry — and the **headless background worker** connected every
> account *before* registering any of them, so every replacement handed back during a cold
> background pass had nowhere to land and was dropped. The next launch then presented a token the
> server had already replaced, which a server that treats a replay as theft answers by revoking the
> whole grant. This killed a real Fastmail account twice, ~2 days apart, while the Microsoft and
> Google accounts beside it were unaffected — Microsoft leaves a superseded token valid and Google
> does not rotate at all, which is why an ordering bug this simple survived a year. Both boot paths
> now register through one helper before anything dials, and the connect result no longer carries a
> config a caller *could* re-register, because re-inserting it put the old token back over the new
> one. The same trap was live in the JMAP **re-authentication** path, which wrote the credential it
> was handed at sign-in rather than the one the registry held, so signing back in did not always
> stick. And a grant the server has explicitly refused is now remembered for half an hour rather
> than re-presented by every provider on the account — the production log shows four such requests
> in under two minutes, each offering a token it had already been told was dead.
>
> A third cause, found on a device while verifying the two above: two background passes can overlap
> (a one-time request and the periodic one are different WorkManager chains), and each built its own
> core, so one account had **two independent refreshers of the same credential** — measured, two
> rotations of one grant 168 ms apart, the second of them a replay of a token the first had just
> superseded. Token state is now shared per account across the whole process, so the second finds a
> valid token and never refreshes; a source built from a *fresh sign-in* replaces that state instead
> of adopting it, which is what keeps a re-authenticated account from carrying on with the dead grant
> it was repaired from. The Android host also skips an overlapping pass outright, so the sharing is
> rarely needed rather than routinely load-bearing.
>
> No separate user-facing note: the symptom is the one already described above — the account asks to
> be signed in again — and a release assembles every pending fragment into one 500-character store
> field, so a second sentence saying the same thing would cost the budget without telling anyone
> anything new.

### Folder names with an ampersand or non-Latin characters — `folder-names-with-an-ampersand` (macos, ios, windows, android, linux, patch)

### A network failure while renewing a sign-in no longer costs you the sign-in — `refresh-failure-is-never-replayed` (macos, ios, windows, android, patch)

> An account's access token is renewed from a stored refresh token, and a server that hands back a
> replacement invalidates the one presented — so presenting it a second time is a replay, which
> Fastmail (and increasingly everyone) answers by revoking the whole grant. Two paths did exactly
> that. The refresh was serialized so concurrent providers could share one result, but only a
> *successful* one: on a failure each waiting provider in turn found nothing cached and posted its
> own request with the same refresh token, so one failed refresh on a JMAP account became eight
> replays — measured, and now a regression test that fails at eight. And every non-`invalid_grant`
> failure was labelled transient and retried, although the one error type covered both a request
> that never left the device and a response the server had already answered into a dead socket; in
> the second case the token was spent and its replacement lost with that response. `reqwest`'s
> failures are now classified by whether the server could have *processed* the request — proven-safe
> only where it is provable, everything unclear treated as possibly-processed — and a body that dies
> after the status line arrives is its own error rather than a transport one. A possibly-processed
> failure backs off instead of re-presenting the token, and stays a retryable error, so it never puts
> a re-authentication prompt in front of the user over a dropped packet. The Android trigger is now
> understood too: a backgrounded app's uid loses network access while the device keeps its network,
> so `getaddrinfo` failed 227 times in five days on one production device — every one of those is
> provably safe to retry, and is classified so.

### A sent message that left no copy in Sent — `sent-copy-never-goes-missing` (macos, ios, windows, android, linux, patch)

> Sending over IMAP is two operations, and only the first one was watched. SMTP dials a fresh
> connection per send, so delivery succeeds over a session that has been idle for an hour; the
> sender's copy is then `APPEND`ed over the provider's standing IMAP session, which by then can be
> dead. That error was discarded — `unwrap_or_else` with the value thrown away — and the receipt had
> no way to express "delivered but not filed", so the outbox recorded `Succeeded`, the UI said
> "Sent", and the copy was gone with nothing anywhere holding the fact. It was reproduced from a
> real store: one submission out of 27, delivered to three recipients (confirmed from the recipient's
> raw message), absent from every folder, with the Sent folder's UIDs contiguous either side of it —
> the server never received the `APPEND` at all.
>
> The filing now retries once on a freshly dialled session, which is what actually repairs the
> common cause. Before appending, the retry asks whether the copy is already there
> (`UID SEARCH HEADER Message-ID`): `APPEND` is not idempotent, and a first attempt that committed
> but lost its response must not become two copies in Sent. When neither attempt files it, the
> receipt carries `SentCopy::Unfiled` with the reason, through `SubmitOutcome` to the core, which
> logs it, ends the send in a new terminal `SendStatus::SentNotFiled`, and raises a **standing
> question** the user can answer: `Surface::UnfiledCopy`, a modal offering to file the copy. The
> status is deliberately neither `Sent` (which is how the copy got lost in silence) nor `Failed`
> (which would tell someone a message that has already reached its recipients did not go, and
> invite a re-send); it shows no hint of its own, because the modal already says it with a button.
>
> The repair is `Provider::file_sent_copy` — it places the copy and **sends nothing**. Making
> delivery and filing one transaction is the tempting fix and the wrong one: the only way to
> guarantee a copy would be to re-run the send, and re-running a send that already succeeded puts
> the message in front of its recipients twice. So the send is never repeated and the filing alone
> is retried, made idempotent by searching Sent for the message's own `Message-ID` first. The
> contract is [`docs/sending.md`](../../sending.md), including the Linux and durability gaps.
>
> Only IMAP/SMTP accounts could hit this: JMAP files the copy with the submission's
> `onSuccessUpdateEmail`, and Graph and Gmail file it server-side. The JMAP path has a narrower
> cousin — its implicit `Email/set` can report the Drafts→Sent move `notUpdated` and that response
> is not read — but there the message is still in the account and still syncs, so it is left as a
> known gap rather than folded into this fix.

### The app stays responsive during a first sync — `the-app-stays-responsive-during-a-first-sync` (macos, ios, windows, android, linux, patch)

> A streamed sync commits one message at a time and signals two surfaces per commit — the mailbox
> list and the sync progress. Only the first was coalesced, and coalescing it achieved nothing:
> the uncoalesced progress signal that followed flushed the pending one on its way through, so
> every message delivered both. Each costs a client a full snapshot pull and list reconcile on the
> thread it renders on.
>
> Measured on a five-account first sync of 7,107 messages: ~26 ms of main-thread work per signal,
> one core saturated for three minutes, and a reading pane the core had published in **1 ms** left
> on its spinner for 2 min 24 s — its signal was queued behind the backlog. Both surfaces are now
> coalesced to at most one notification each per 250 ms. A signal carries no payload, so the host
> still reads current state, the trailing fire after the last commit still delivers the final one,
> and a download that finishes inside a window simply never raises a bar.
>
> The body warm that follows a sync — the longer half of a first sync, nearly six minutes on the
> largest account measured — reported nothing at all and now names itself in the same status line.
>
> On Apple the signal was amplified again on arrival. `MailboxModel` was one `ObservableObject`
> carrying 37 published fields, all sharing a single change notification, so a mailbox signal —
> which writes ten of them — invalidated every view bound to the model: the reading pane, the
> sidebar, the composer, the settings screens. Observation is now per property, so a view
> re-renders only for what it actually reads.
>
> Coalescing caps what reaches a client; it cannot touch what the core does before it signals. A
> streamed pass committed one message at a time, and every commit spliced the cached rows, re-sorted
> them and rebuilt the visible list — so the download cost a full list rebuild per message, on the
> sync thread. Commits are now bulk: the same 200 messages rebuild the list 5 times instead of 201,
> and the store, the thread derivation and the recipient backfill each run per chunk rather than per
> message.
